UPTIME_TRUST_PROXY_HOPS is 0, so it trusts none of it: every browser counts
as the UI pod, one shared lock per name, and the backend log warns. Set it
to the X-Forwarded-For entries your proxies in front of the UI write
(README, "Hesaplar ve giriş", has the values and how to check them):
{{- if .Values.route.enabled }}
  a plain Route: 1; a Route behind a WAF or L7 load balancer that writes
  X-Forwarded-For: 2
{{- else }}
  ingress-nginx with its default settings: 1; GKE's own Ingress (GCE): 2;
  an L7 Google Cloud load balancer in front of ingress-nginx with
  use-forwarded-headers and compute-full-forwarded-for: 3
{{- end }}

  --set-string backend.extraEnv.UPTIME_TRUST_PROXY_HOPS=1

WARNING: neither a heartbeat (heartbeat.urlSecret, or UPTIME_HEARTBEAT_URL
in backend.extraEnv) nor the alert rules (metrics.prometheusRule.enabled)
are on, so nobody hears when Kubeat itself fails: with no backend pod
nothing is checked, with a full data volume every check result is lost,
and either way no notification is sent. A heartbeat to a receiver outside
the cluster (healthchecks.io, an Uptime Kuma push monitor, ...):
  kubectl -n {{ .Release.Namespace }} create secret generic {{ .Release.Name }}-heartbeat --from-literal=url=https://<heartbeat-address>
  helm upgrade {{ .Release.Name }} oci://ghcr.io/yusufceng/charts/kubeat --version {{ .Chart.Version }} -n {{ .Release.Namespace }} --reset-then-reuse-values --set heartbeat.urlSecret.name={{ .Release.Name }}-heartbeat
The heartbeat does not hear a channel that takes no notifications; the
alert rules do, per channel (KubeatNotificationsFailing), and only the
heartbeat is heard when the whole cluster is down. Best both.
